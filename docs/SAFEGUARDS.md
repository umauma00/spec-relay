# 守っていること

キットが移行の途中で必ず守る決まりと、それを確かめる仕組みです。要点は [README](../README.md#守っていること) にあります。

- **元のコードは書き換えない。** すべてのエージェントにとって読み取り専用です。
- **仕様の確定は人が決める。** AI は人が認めた項目だけをチェックし、明示的な承認なしに archive しません。レビューはチャットで1項目ずつでも、ファイルや PR でまとめてでもかまいません。archive の前に `scripts/gate.mjs review` で、すべての要件・画面・質問・コンテキストがチェックリストにあり、チェック済みで、質問への判断とレビュー担当の名前が書かれ、AI の照合が解決し、元ファイルがすべて調査に含まれ、除外していないファイルがどれかの capability の解析に含まれ、すべての要件に元コードの位置があり、元コードのすべての箇所（メソッドや関数など）が要件・画面に覆われているか判定済みであることを確かめます（`openspec archive --yes` 自体はこれを確かめません）。
- **書いた本人でない AI が3つの切り口で確かめる。** 調査では、別の AI が inventory の行ごとにファイルを読み、除外や carry のファイルに動作がないか、入口がどの capability にもないことがないかを確かめます。解析では、別の AI が要件ごとに元コードと突き合わせ（照合。書き漏れの `incomplete` も止める）、箇所ごとに抜けを探し（箇所台帳）、入口ごとに処理を最後まで追って、動作ごとにそれを書いたシナリオの名前を挙げます（入口からの見直し）。どれも gate が結果を確かめ、未解決のものがあると止まります（[詳しく](WORKFLOW.md#入口からの見直し0300-から)）。
- **機能どうしの仕様も突き合わせる。** 仕様は機能（capability）ごとに別の解析担当が書き、互いの仕様を読まないので、それぞれが元コードと合っていても、接する所で食い違うことがあります。解析では gate が、source-map の Dependencies に入口からの見直しで他の機能に任せた先がすべてあるか、使うと書いた相手の入口が相手の archive 済みの source-map に実在するか、持ち主でないコンテキストがテーブルに書き込んでいないか（調査のコンテキストの地図と plan の `## Shared data`）を機械的に確かめます。そのうえで、確定した仕様（ベースライン）を持つ機能とのつながりのある組（一方が他方を使う、同じ DB のオブジェクトを使い一方が書き込む、同じファイルを持つ）ごとに、別の AI が両方の仕様を読んで `consistent`・`conflict`・`duplicate`・`term`・`unclear` を判定し、プロジェクトで1つの台帳 `openspec/spec-relay/consistency.md` に残します。行には両方の仕様の符号が入り、どちらかの仕様が変わると照合し直しになります。解析の gate、`gate.mjs port-ready` と `port-done`、仕上げが、未照合や未解決の組で止まります。人が違いを残すと決めた組は、plan の `## Consistency decisions` に決定として残ります（[詳しく](WORKFLOW.md#機能どうしの整合性0310-から)）。
- **実装の前後も確かめる。** port は、調査・移行先の設計・ベースライン仕様がそろい、修正中でなく、ほかの確定した仕様との組がすべて照合済みであることを `gate.mjs port-ready` で確かめてから始めます。archive の前に `gate.mjs port-done` が、すべてのタスクの完了、着手時から仕様が変わっていないこと（ハッシュ）、今のコードでテストと境界チェックと選んだ比べ方が通った記録（`verify.mjs` が実行して書く）、仕様のシナリオごとのテスト、`TODO(port)` が残っていないこと、照合担当が新しいコードを元コードと突き合わせた結果を確かめます。比べ方が A だけのときは、同じ動きであることは元を動かして比べたのではなく推定だ、と完了時に知らせます（[詳しく](WORKFLOW.md#実装が終わったときの確かめ方)）。元のプログラムを動かせるか本番の記録があれば、比べ方 B1 で、元が返した結果と新しいコードの結果を `compare.mjs` が1件ずつ比べます（[詳しく](COMPARE.md)）。
- **すべてのシナリオに自動の確認を付ける。** シナリオごとに、画面のテスト（`e2e`）・元のプログラムの記録との比較（`compare`）・単体テスト（`unit`）のどれで確かめるかを port の design.md に書き、確認のないシナリオがあると `gate.mjs port-done` が止まります。web の画面のシナリオは Playwright のテストにし、**同じテストをまず元のシステムで通してから**新しいシステムに流します（`e2e.mjs`、比べ方 B2）。元のシステムで通ることがテストの正しさの証拠になり、そのあとにテストを変えると元のシステムでやり直しです。同じテストが元のシステムで撮ったスクリーンショットと、新しい画面も比べます（比べ方 C）。要素は id や class ではなく、役割・ラベル・文字で指します（[詳しく](E2E.md)）。
- **最後に全体を確かめて引き渡す。** 全 capability の port が終わったら、`scripts/finish.mjs` が `TODO(port)`・計画の `## Follow-up`・各 port のリスクを機械的に集めます。全体のビルドとテスト、選んだ比較をやり直した結果を記録し、そのあとにコードが変わると `gate.mjs review` が止めます。残りものは1件ずつ「切替の前に直す」「切替の後の課題」「直さない」に分類して人が決め、報告には確かめられたことだけを書きます（元のプログラムと比べていないコンテキストはそう明記します）。本番への切替やデータの移し替えはキットの範囲外で、報告に「切替の前にやること」として残します。
- **画面の見た目は方針で決める。** 見た目まで同じ（`same`）、配置と文言は同じ（`layout`）、作り直す（`new`）のどれにするかを、移行先の設計でコンテキストごとに1回だけ人が決めます。CSS・画像・フォントなど変換しないファイルは調査で `carry` にでき、`gate.mjs port-done` がコピーの中身が元と同じかを確かめます（[詳しく](WORKFLOW.md#画面の見た目)）。
- **データベースもコードと同じに扱う。** ストアドプロシージャ・トリガー・ビュー・制約・ジョブにあるロジックも移行の対象です。調査で、使っているデータベースと定義の場所を `database.md` に記録し、リポジトリにない定義は人が書き出して `openspec/spec-relay/db/` に置きます（元コードと同じく読み取り専用で、inventory に入ります）。移行先の設計の `data.md` で、スキーマの方針（既定はそのまま使う）、DB の中のロジックを種類ごとに残すか移すか、SQL 方言と ORM の違いの規則、テスト用のデータベースを一度だけ決めます。調査のあとで定義が変わると gate が止めます。AI はデータベースに接続しません（[詳しく](DATABASE.md)）。
- **仕様の修正は読み違いと書き漏れだけ。** 動きそのものを変えたいときは、移行後の別作業にします。実装担当は、元コードにあって仕様にない動作を見つけたら、作らずに報告します。黙って落とすことはありません。
- **正は markdown、見るのは HTML。** レビューでは `scripts/render.mjs` が成果物を1枚の HTML にします（要件ごとのカード、シナリオ、元コードの該当行、質問と判断、進み具合）。デザインはスクリプトに固定しているので、どのモデルでも同じ見た目になります。判断は markdown（review.md）に記録します。承認済みの仕様（`openspec/specs/`）も `--spec` で同じデザインの読みもの（一覧と capability ごとのページ、検索つき）にできます。
- **仕様が契約。** 実装中に元コードと仕様が食い違ったら、AI はどちらかを選ばず人に聞きます。実装担当は「良かれと思って」の手直し（仕様にない機能、画面の今風の作り直し、入力チェックやエラー処理の追加、元のバグの修正、決めていないライブラリの追加）をしません。
- **同じ指摘を2回させない。** レビューなどで人が直したことのうち、ほかの capability でも起きそうなことは、オーケストレーターが `openspec/spec-relay/lessons.md` に書き残し、次の解析担当と実装担当が読みます。書くのは人の言葉からだけで、書く前にその1行を見せて了解をもらいます。照合担当には渡しません（[詳しく](WORKFLOW.md#レビューの学びを次へ渡すlessonsmd)）。
- **並列で進めても、レビューは1本。** 解析・照合・実装はサブエージェントが同時に進め、人のレビューは1つずつです。先に解析しておくのは `--ahead` 件までにして、レビュー待ちを溜めません。サブエージェントは割り当てられたファイルだけを書き、オーケストレーターには短い報告だけを返すので、長い移行でもオーケストレーターの文脈が埋まりにくくなっています（[詳しく](WORKFLOW.md#並列での進め方)）。
- **工程を飛ばさない。** 次の工程に進む前の確認は `gate.mjs` がします（解析の承認には調査の archive と、調査の一覧にある capability が必要。実装の開始には調査・移行先の設計・確定した仕様が必要）。「飛ばして」と頼まれても、AI は確認を外さず、その工程が守っているものと最短の進め方を説明します。gate を実行するのはオーケストレーターなので、フックが無効の間は AI が指示を守ることが前提です。フックを有効にすると、gate を通らない archive と、元コード・確定仕様・設定への書き込みを Copilot が実行前に拒否します（[フック](TROUBLESHOOTING.md#フック試験中既定は無効)）。
- **進捗は Copilot の TODO に出す。** `scripts/status.mjs` が `openspec/` のファイルから進捗を計算し、オーケストレーターが「全体1行 + いまの機能の工程 + 並行して動いている機能」を TODO リストに出します。報告の先頭にも同じ一覧を出します。TODO のチェックは承認になりません（[詳しく](WORKFLOW.md#進捗の表示copilot-の-todo)）。
- **かかった時間を残す。** 工程ごとに、進行中の時間とレビューなどで人を待っていた時間を分け、サブエージェントの作業時間も記録します。トークン数は Copilot がフックに渡さないので記録せず、`/usage` を貼ったときだけメモに残します（[詳しく](WORKFLOW.md#かかった時間の記録)）。
